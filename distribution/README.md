# OpenCore Windows distribution

Every successful push to `main` runs `.github/workflows/build.yml`, verifies the current UI/runtime repairs, creates and signs the new complete **OpenCore Package.exe**, reuses the permanent **OpenCore Setup.exe** and its original signature byte for byte, and publishes a stable GitHub release plus `latest.json`. The setup is a permanent 483,328-byte file, limited to 2,000,000 bytes. Users keep the same file for every app version; installed apps update through their own update button. It always fetches the latest completed public release, displays resumable download progress, verifies the SHA-256 and pinned OpenCore signature, then opens the complete installer. The updater feed points to the complete package so in-app updates retain their normal quiet installation and restart behavior.

The installer filename and caption do not contain a version. Internal release versions are `0.3.<Actions run number>` so all new releases are newer than existing `0.2.305` installations. Windows Apps shows the distribution version, and the app header compares that version with the signed update feed. Checking metadata never downloads or installs a package. The user presses **Update ready** once to start the update. The same button shows **Updating…** and disables repeat clicks while the update runs. The app reopens after an updater installation.

Setup, uninstaller, app shortcuts and the browser extension use the official OpenCore logo. `sync-branding.py` copies the canonical 32/128px icon assets into the extension and refreshes the pairing page logo and favicon before packaging.

## Recovery boundary

The newer native checkout was lost before this recovery. The repository's historical native source was last published as 0.2.142 and cannot replace the newer installed native behavior. `baseline.json` therefore pins the verified original 0.2.305 native executable and clean runtime resources as GitHub release inputs. No chats, credentials, browser profiles, accounts, managed environments or downloaded model weights are included.

`recovered-dist/` is the exact recovered frontend source. `build-ui-repair.cjs` applies reviewed function-level patches, adds the managed Hugging Face extension, and emits the current frontend. `patch-executable.cjs` checks the original native hash, asset addresses, lengths, compressed budgets, and native catalog hashes before replacing only declared data slots. Native machine code remains unchanged. `resource-map.json` maps installed helpers to their canonical source in `src-tauri/resources/`, `reflex/` and `chrome-extension/`; runtime tests import those same files so a separate snapshot cannot drift from the shipped code. The original native executable's file version remains 0.2.305; the distribution version and commit are recorded in installed `build-info.json` and displayed by the current frontend.

Until the missing native source is restored, **the distribution sources in this directory are the frontend inputs used for release**, and `resource-map.json` selects canonical managed resources from the normal source folders. The historical `src/` and `src-tauri/src/` remain available for source restoration; edits there alone cannot alter the preserved native executable. The pipeline refuses native-source changes without a matching restored baseline rather than silently publishing an executable that ignores those changes. Do not switch the release back to compiling the older checkout without porting and verifying the missing newer functionality.

## Build

On Windows with Node, Python and NSIS available, install the root and `distribution/` npm dependencies, set `OPENCORE_RELEASE_VERSION`, then run `python distribution/prepare.py --inputs <new-input-folder>`. That fetches the pinned public inputs, verifies hashes, extracts to a disposable folder and overlays committed source. Use `distribution/package.py --help` to generate or compile the full installer. The workflow is the complete command reference.

The downloaded package includes a clean Python 3.12.10 standard library and ensurepip, bundled Node helpers and the native inference engine. It installs Microsoft WebView2 if missing. Supported model-specific managed dependencies prepare when that model is installed. Model weights are separate downloads.

Flint, Raon and EdgeRock GGUF variants use isolated, checksum-pinned Windows CPU engines with two threads and ECHO archive retrieval. Flint uses upstream llama.cpp b11860; Raon uses the publisher's pinned RDA/mHC fork; EdgeRock uses the reviewed publisher RMA port built for Windows. Installation verifies the checkpoint, prepares the engine, generates a real response, and verifies another response through ECHO before showing Ready. A low-memory guard stops only the owned worker. The original safetensors, MLX and NVFP4 publisher formats remain visible with their actual runtime requirements; selecting a GGUF variant enables the integrated Windows path. Availability on Hugging Face does not imply every format or model fits every computer.

Built-in cards load their quantization menus from the bundled, immutable package catalog. The user selects a quant and presses **Install** directly. There are no community-search controls or repository-inspection steps on these cards. `hf-research/bundled-quantizations.json` and the explicitly tracked snapshots record the maintainer's source research; `build-publisher-catalog.py --check` verifies that the shipped packages match those inputs without network access. Different fine-tunes, draft companions, duplicate publisher copies and unidentified formats do not pad the minimum. `builtin-quant-coverage.json` records both covered families and remaining exceptions; the universal five-quant minimum is not falsely asserted while exceptions remain.

The separate **Add from Hugging Face** importer checks only the repository entered by the user. It lists that repository's published packages, including quantizations, and retains optional private/gated access through Settings. The app ships pure checkpoint-lineage checks for grouping imports with existing cards; the network research utility stays in `distribution/` and is not shipped as an app feature. Existing installed native profiles remain selectable on their model's card. Native removal opens the original dialog, including shared-file review, external-checkpoint confirmation and the backend's returned scope/token. Non-text downloads keep their category and actual adapter requirements.

Progress requests carry a catalog revision, so unchanged polls omit the large package list and reuse its hydration result. Catalog mutations and job-state transitions invalidate the snapshot; external file changes are rechecked within 30 seconds. Health probes stay small and do not scan model files, preserving the desktop launcher's one-second health deadline. Model use still verifies files independently.

Visited support tabs now retain their existing contents, including Models search, quant selections and scroll position. Hidden support pages pause their page-level reads. The model library shares completed reads and keeps an account-scoped, schema/version-checked IndexedDB snapshot of model metadata for the next launch. It displays saved cards while a single background read checks the current catalog. Installation receipts, removals, Hub catalog changes and returning to the app update that snapshot without clearing the visible library. Active download progress, account credentials and conversations are never persisted in this cache; runtime readiness and installation admission still use the live backend.

Startup retries temporary account-helper failures every half second during initial preparation and opens the workspace as soon as the authenticated account is ready. It shows a normal opening screen during this grace period. A recovery button appears only after a sustained one-minute failure; signed-out users still see sign-in, and account switching cancels obsolete retries.

The bundled catalog contains 933 packages in 176 families, including eight EdgeRock GGUF choices, 25 Tess 4.5 choices, and 23/13/10 choices for Spark X2.6 4B, X2.5 4B and X2.5 1.7B. Newly integrated GGUF presets prepare the pinned Windows CPU engine automatically; publisher-specific EdgeRock and Raon forks take precedence. `community-runtime-verification.json` records actual generation and streaming for five EdgeRock quants on Windows, a local EdgeRock Q3_K_M run, Tess IQ2_XXS, and the tested Spark Q4_K_M variants through ECHO. Those results do not certify every larger variant; installation still requires verification on the user's machine. `publisher-runtime-verification.json` retains the earlier Flint and Raon results.

Large checkpoint files download through eight bounded range workers with at most 64 MiB of chunk buffers. Only contiguous verified-length ranges extend the resumable partial file; whole-file hashes are checked before publishing the receipt. Servers that ignore range requests fall back to sequential transfer. Disk preflight accounts for matching partial files and retains a 2 GiB reserve.

`permanent_bootstrap.py` checks and copies the exact setup and signature from `bootstrap/permanent/`; it never invokes a compiler or changes them to match the app version. `build-bootstrap.py` remains a separate maintenance/recovery tool for the downloader source, with its pinned verifier, notices and official logo. App releases do not call it. `qa-bootstrap.py` runs the resulting EXE against a real signed package and rejects damaged signatures and checksums. `--download-only <report-path>` exercises the public download and verification without launching an installer. The ordinary EXE opens the full installer after verification.

`/S /TEST /D=<new-absolute-folder>` extracts app and clean Python into an isolated verification directory. It skips user-profile runtime writes, registry, shortcuts, WebView2 installation, app launch and uninstaller creation. `qa-share-installer.py` compares all extracted files to the package manifest and runs the clean interpreter. The regular installer and uninstaller use the official logo from `src-tauri/icons/`.

Updater behavior follows the [Tauri updater protocol](https://v2.tauri.app/plugin/updater/). Release publication occurs only after the artifact signature and isolated extraction checks pass.

The Windows build retains its verified signed installer as an Actions artifact for seven days. A separate publication job consumes those exact bytes. If GitHub publication fails, rerun only that failed job to reuse the tested installer. Draft creation uses the release ID returned by the API, and draft metadata is refreshed by ID because the release list can remain stale immediately after creation.

Four more built-in cards are included: HobbyLM 1B Computer Use, Mano-CUA 2.0 4B, Terminal-RSI 27B and DiscoveryRSI 27B (the last repository ends in 27B). They add 72 immutable packages with direct preset installation. Mano has 12 GGUF quants; Terminal-RSI has 26 and DiscoveryRSI has 27. Their original checkpoints and verified specialized publisher conversions remain visible with runtime requirements. HobbyLM is a single LoRA adapter package, including adapter_config.json; it requires a separate base model and the publisher's macOS/MLX action harness, with no integrated Windows adapter. These are model integrations, not installations of the publishers' agent harnesses. Source metadata is frozen under distribution/hf-research/requested-models, and the compiler includes it without online search.

The requested Tiel-Coder 35B A3B APEX-I-MiniPlus V2.1, Tals-coder-flash-02 and Kestrel 4B Coder cards are also included. Tiel APEX and Tals each retain their single published custom package and matching vision projector; Kestrel offers BF16 plus its publisher's Q8_0 GGUF and projector. These editions are kept separate from Ornith, Cyber-Tiel, Ternary Bonsai and Qwen training bases. Tals requires a publisher-compatible llama.cpp build with Hadamard kernels; it is downloadable with that requirement shown and is not advertised as having an integrated Windows execution adapter. The other packages still require a real generation check before Ready. No publisher speed claims, vision execution or MTP acceleration are certified by the catalog addition. The single-button Update ready action remains in this release.
